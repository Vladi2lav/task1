# Архитектура проекта

Итоги торгов бирж ETS и Каспий: сбор → единая БД → веб-портал.

## 1. Что за данные и зачем

Товарные биржи Казахстана (зерно, уголь, нефтепродукты, цемент, сахар, газ) каждый торговый день публикуют итоги: кто у кого что купил, сколько и по какой цене.
Публикуют в разном виде: ETS выкладывает ежедневные XLSX-файлы, Каспий показывает данные на сайте. Свести обе биржи в одну таблицу с поиском и фильтрами — задача проекта.

## 2. Источники (результат анализа)

| | ETS (ets.kz) | Каспий (ccx.kz) |
|---|---|---|
| Официальный API | нет | нет публичного; у сайта есть внутренний `/api/internal/trading-results` |
| Формат | страницы «год → месяц → день», на каждый день XLSX-файл | страница `/trading-and-analytics/trading-results` с фильтрами (`date_from`, `date_to`, `product_code`, `section_code`, `tn_ved`, `buyer_name`, `seller_name`, `broker_*`, `delivery_term`, `page`, `per_page`) |
| Способ сбора | requests + BeautifulSoup (обход страниц) + openpyxl (чтение XLSX) | requests (HTML/JSON); Playwright только если понадобится |
| Готовых парсеров на GitHub | не найдено | не найдено |

Подробности и колонки — в `docs/SOURCES.md`.

## 3. Стек

Python 3.11, **Django 5.2**, SQLite (можно сменить на PostgreSQL через переменную окружения), requests, BeautifulSoup + lxml, openpyxl, APScheduler, pytest. Интерфейс — шаблоны Django + vanilla JavaScript (fetch, без перезагрузки страницы).

## 4. Структура репозитория

```
config/              настройки Django (settings, urls)
exchanges/           модели БД, админка, миграции
scrapers/            парсеры
  base.py              общий интерфейс BaseScraper и формат записи TradeRecord
  normalize.py         приведение дат, чисел, единиц, регистра, ИНН/БИН
  ets.py               парсер ETS
  caspy.py             парсер Каспий
  runner.py            запуск парсера, защита от дублей, журнал запусков
  scheduler.py         ежедневный запуск (APScheduler): итоги торгов, затем новости
  news.py              новости бирж: парсеры лент ETS и Каспий, сохранение без дублей
  management/commands/ collect_trades, collect_news, run_scheduler
portal/              веб-портал: страницы, JSON API, шаблоны, статика
docs/                архитектура, источники, описание БД
tests/               тесты парсеров и API
scraper.toml         расписание, паузы между запросами, глубина истории
```

## 5. Поток данных

```
 сайт биржи ──> Scraper (ets / caspy) ──> TradeRecord (единый формат)
                                             │ normalize
                                             ▼
                          runner: upsert по уникальному ключу ──> БД (SQLite)
                                             │                       ▲
                                             ▼                       │
                                         ParseRun (журнал)     портал читает только БД
```

Портал никогда не обращается к сайтам бирж.

## 6. Модель данных

- `Exchange` — биржа (ETS, Каспий).
- `Product` — товар: название, код товара, код ТН ВЭД.
- `Participant` — покупатель/продавец: название, БИН (уникален по БИН, если он есть).
- `Broker` — брокер (по названию).
- `Trade` — одна строка итогов торгов: биржа, дата(+время), товар, покупатель, продавец, брокеры покупателя и продавца, количество сделок, объём + единица, цена (с НДС / без НДС / средневзвешенная, мин., макс., открытие, закрытие), сумма, базис и срок поставки, `source_key` (уникальный отпечаток строки), ссылка на источник, `parse_run`.
- `ParseRun` — журнал: время старта/конца, биржа, добавлено/пропущено записей, статус, текст ошибки.

Индексы: дата торгов, биржа, товар, участники, брокеры, сумма. Описание — `docs/DATABASE.md`.

### Защита от дублей
`source_key = sha1(биржа | дата | покупатель БИН/название | продавец БИН/название | код товара | базис | цены | сумма | номер повтора в файле)`. Поле `UNIQUE`; вставка через `get_or_create`/`ignore_conflicts`, поэтому повторный запуск ничего не удваивает.

### Отсутствующие поля
Если биржа поле не отдаёт (например, ETS не публикует объём и срок поставки), поле остаётся пустым. Объём ETS можно вывести как сумма / средневзвешенная цена — помечается отдельным флагом в документации.

## 7. Парсеры

Общий интерфейс:

```python
class BaseScraper:
    exchange_code: str
    def fetch(self, date_from, date_to) -> Iterable[TradeRecord]: ...
```

- Паузы между запросами (по умолчанию 1–2 с), заголовок User-Agent с описанием, повторные попытки с задержкой, таймауты.
- Любая ошибка источника (сайт недоступен, структура изменилась) → запись в `ParseRun` и в лог; ранее собранные данные не затрагиваются, потому что запись идёт транзакциями по файлу/странице.
- **ETS:** обойти `/documents/trading-results/` → год → месяц → ссылки на `.xlsx`; скачать, прочитать строки таблицы, пропустить итоговую строку.
- **Каспий:** запрос страницы/JSON с фильтром по датам и пагинацией; разбор таблицы.

## 8. Планировщик

`python manage.py run_scheduler` — процесс APScheduler, расписание из `scraper.toml` (по умолчанию ежедневно в 18:30 по Астане, после окончания торгов). Ручной запуск: `python manage.py collect_trades --exchange ets --since 2026-07-14`. Тот же запуск есть кнопкой на странице состояния.

## 9. Веб-портал

- `/` — таблица торгов: пагинация, сортировка по столбцам, по умолчанию свежие сверху.
- Фильтры (комбинируются, без перезагрузки): биржа, период, товар/ключевое слово, продавец/покупатель (название или БИН), брокер, диапазон суммы, место поставки.
- `/api/trades/` — JSON (фильтры + `page`, `page_size`, `ordering`). Фронтенд — fetch по этому API.
- `/analytics/` — сводка и 4 графика (Chart.js, локальная копия в `portal/static/portal/vendor/`): динамика средневзвешенной цены товара, оборот по дням, топ-10 товаров и топ-10 участников по сумме. Данные — `/api/analytics/` (фильтры `exchange`, `date_from`, `date_to`, `q`, товар — `product_id` или `product_code`); расчёты в `portal/analytics.py`. Записи без суммы (NULL) в суммы и топы не входят, их доля возвращается в ответе (`summary.share_without_amount`).
- `/status/` — последнее обновление по каждой бирже, число записей, итог последнего запуска, кнопка ручного запуска (`/api/collect/`).
- `/api/trades/export.xlsx` — экспорт текущей выборки в Excel (не больше `PORTAL_EXPORT_MAX_ROWS` строк).
- `/news/` — лента новостей бирж (фильтр по бирже и тексту), данные — `/api/news/`. Новости собирает `scrapers/news.py`
  (`manage.py collect_news`; ETS — `/press_centre/news/`, Каспий — `/news/category/announcement` и `/corporate`),
  планировщик запускает сбор после итогов торгов, если `[news].enabled` в `scraper.toml`.
- `/legal/terms/`, `/legal/privacy/`, `/legal/cookies/`, `/legal/sources/` — пользовательское соглашение, политика
  конфиденциальности, cookie, источники данных и лицензии (`portal/legal.py`); реквизиты владельца — из настроек
  `SITE_OWNER`, `SITE_CONTACT_EMAIL`, `SITE_HOSTING_PROVIDER`, `LEGAL_EDITION_DATE`. Cookie-баннер — в `base.html`.
- Режим только для чтения `PORTAL_READ_ONLY` (на Vercel всегда): кнопка сбора скрыта, `/api/collect/` отвечает 403.
- `/healthz` — проверка работоспособности (приложение + БД) для Docker и мониторинга (`config/health.py`).

Развёртывание (Windows `start.bat`, Docker, Vercel) — [DEPLOY.md](DEPLOY.md).

## 11. Ограничения и риски

- Структура сайтов может измениться — парсеры изолированы, ошибки не затирают данные.
- Каспий: из тестовой среды таблица итогов приходит пустой; формат подтверждается на реальных данных (см. `docs/SOURCES.md`).
- Парсинг ведётся мягко: паузы, один поток, только публичные страницы.
